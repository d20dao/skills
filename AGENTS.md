# d20dao integration guide for agents

These skills support readers and assistants using the general d20dao randomness service. They do not grant access to an operator, a wallet, a bot or a deployed contract. Choose the relevant self-contained skill and inspect the installed @d20dao/vrf-sdk declarations and public provenance.

The main task is adding randomness to an existing application contract. Begin with [d20-consumer](skills/d20-consumer/SKILL.md), its [deployment reference](skills/d20-consumer/references/arc-testnet.md), [method table](skills/d20-consumer/references/methods.md) and [consumer example](skills/d20-consumer/assets/RandomnessConsumer.sol). Preserve existing authorization, storage, initialization and payment rules. The constructor-based example is not a drop-in initializer for upgradeable applications. Use keeper operations only when the user is actually operating a keeper.

- Use d20-consumer for D20VRFConsumer/ID20VRF integration, fee quoting, refund credit, callback authentication and deterministic mappings.
- Use d20-lifecycle for pending publication, target readiness, timely acceptance, batch fulfillment events, same-result callback retry and fixed-recipient refunds.
- Use d20-verification for trusted proxy/epoch/request evidence and public replay. RequestContext includes original requestBlock and resolved targetBlock; replay configuration uses initialFeeRecipient and initialMinFee, and the signer catalog in force for the request's epoch.
- Use d20-sdk for public exports, ABI/initializer shapes, Solidity imports, off-chain fee quoting and npm package usage.
- Use d20-keeper for authorized operator setup, observation and recovery, including implementation pins, fee budgets and one durable nonce lane.

Fees: `max(minFee, feeMultiplier × baseFee × (fulfillGasOverhead + callbackGasLimit))` in native USDC (18 decimals), read live with `pricing()`. Contracts pay `quoteFee(callbackGasLimit)` in the requesting transaction (exact). Off-chain senders quote `quoteFeeAt(callbackGasLimit, latestBlock.baseFeePerGas)` plus a buffer, since `eth_call` commonly reports a zero base fee. Underpayment reverts with `IncorrectFee(expected, actual)`; excess is refund credit of the refund address, withdrawable with `withdrawRefundCredit`. Each request settles keeper share, treasury share and refund from the fee it escrowed (`requestFeePaid`); an expiry refund pays `feePaid × refundBps / 10000` with the ratio snapshotted at request time (`requestRefundBps`, default 100%; the owner can lower it for future requests, never below 50%). `refundBps()` is only the ratio for future requests; the keeper/treasury split uses `keeperFeeBps()` at acceptance.

Results and recovery: take `requestId` from the coordinator's `RandomnessRequested` log; poll the latest block, then `getRequest(requestId)`. `fulfilled` is final (`getMappedResult`); not fulfilled after `deadline` is expired and refundable, never fulfilled late. `refundRequest`, `retryCallback` and `retryRefundCallback` revert `InsufficientCallbackGas` rather than forward less gas: use 400,000, `gasLimit + 250,000` and `gasLimit + 150,000` transaction gas. Front ends: `wallet_addEthereumChain` with chain ID `0x13b2` (Arc Mainnet) or `0x4cef52` (Arc Testnet) and USDC with 18 decimals; decode coordinator errors with `coordinatorAbi`; ethers `Result` fields named like array members (`values`, `length`) need `getValue(name)`. Observed 2026-09-17, not guaranteed: `*.arc.io` RPC endpoints are blocked by common ad-block lists and some limit JSON-RPC batches, so read through the wallet provider or a same-origin read-only relay (https://github.com/d20dao/randomizer-demo) and lower ethers' `batchMaxCount`. Every coordinator and registry function, event and error, with responses: https://github.com/d20dao/d20-sdk/blob/main/API.md.

Epochs last 200 blocks; each uses the catalog in force for it, 1 to 10 registered recipes with their signers, and accepts only signed data its recipe's data template matches exactly. The keeper prepares snapshots locally without idle publication. Live paid demand publishes the first saved packet and binds randomness to max(requestBlock,commitBlock+1); the attestation may be at most 240 seconds old at publication. Keep the original 60-second deadline, mapping, epoch and refund recipient; do not reroll to recover failed delivery. Unused local snapshots can remain for 50 epochs with live-work protection. `fulfillRandomnessBatch` serves up to 16 requests per transaction with unchanged per-request events; skipped members emit `FulfillmentSkipped`.

Both service endpoints are initialized UUPS proxies with two-step owners; `renounceOwnership` is disabled. Stable addresses do not identify implementation code: verify both implementation histories and initialized configuration. Upgrade authority is trusted. The registry committer, backup committers, coordinator payout/share, bounded pricing and refund ratio are administrable; the registry owner appends immutable recipes (`registerRecipe`, `RecipeRegistered`) and schedules a catalog of registered recipes and their signers for epochs at least two ahead (`scheduleCatalog`, `CatalogScheduled`, read with `catalogAt`). There is no request-input or VRF-key setter.

Configure CHAIN_ID explicitly; Arc is one network, not an assumed default or service name. Telegram is opt-in and configured-chat-only with read-only /status and /keeper; no access is available by default. Public evidence and receipts are authoritative, while health and notifications are observations. Consumer integration does not authorize upgrades, key access, funding, bot messages or publishing.

Install `@d20dao/vrf-sdk` (0.4.0 or newer) from npm. The Getting started and Copy prompt resources on the d20dao.org website are backed by `https://d20dao.org/llms.txt`, `https://d20dao.org/llms-full.txt`, `https://d20dao.org/agents.md` and per-guide plain-text prompts. Deployment manifests are `https://d20dao.org/deployments/arc-mainnet.json` (chain 5042, live) and `https://d20dao.org/deployments/arc-testnet.json` (chain 5042002, development). Respect the user's requested task and use the relevant skill rather than treating an integration prompt as operator authorization.
