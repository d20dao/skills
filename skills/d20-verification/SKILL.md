Public protocol reference: `fa6417dc4667cc98e298c4280a4bfe98fc8b7873`. Match the installed SDK provenance and the deployed implementation history before use; each deployment manifest records the source its implementations were deployed and upgraded from.

Use the public @d20dao/vrf-sdk, version 0.6.1 or later (0.5.0 or later suffices for Arc alone): 0.4.0 cannot replay a drand epoch and throws `Expected canonical 65-byte low-s EIP-191 signature` on its 64-byte BLS signature. Read its current declarations, provenance and replay/epoch/evidence/mapping sources. Match the reviewed code and both proxy implementations for the relevant transactions; proxy addresses alone do not identify executed logic. Keep keeper/prover keys outside verification.

## Arc

1. Pin chain, effective D20VRFCoordinator/EpochEntropy addresses, implementation histories, initialized public key and configuration independently of submitted proof. Retrieve successful receipts/state and validate log emitters.
2. Source anchor is epochStart-1. Resolve the catalog in force for the request's epoch: the initial catalog (recipes 0 to 3, `catalogHash()` and the initial signer getters) unless a `CatalogScheduled(fromEpoch, catalogHash, recipes, signers)` event with fromEpoch at or below that epoch applies; `catalogAt(epoch)` returns the same hash, recipe ids and signers, and `Epoch.catalogHash` records it. `resolveEpochCatalog` turns that view into the catalog replay expects. A scheduled catalog applies only to epochs at least two ahead of its scheduling and is a trust event. Decode original EpochCommitted evidence and replayEpochCommitment using its exact packet, that catalog, anchor, record and actual publication block/time; the record's timestamp (a beacon round's scheduled time) must not be after publication or more than 240 seconds before it. Publication is on demand and may occur after the first request or an epoch boundary.
3. Each catalog slot is a registered recipe, appended by the owner and never edited or removed, so an old epoch keeps replaying with the recipe it used. A signed-record recipe (`registerRecipe`, `RecipeRegistered`, `getRecipe`) is a canonical request, a data template fixing the exact signed record and a gateway body; a beacon recipe (`registerBeacon`, `BeaconRegistered`, `beaconOf`) names a drand network. The catalog in force is `[11]`, the drand evmnet beacon alone with no fallback source, since epoch 11319 on Arc Testnet and epoch 12448 on Arc Mainnet. Earlier epochs came from signed API records under other catalogs, and replay still verifies them; `catalogAt(epoch)` is what decides. The SDK's `BUILTIN_EPOCH_RECIPES` covers recipes 0 to 5; read any other registered recipe with `readEpochRecipes` and put it in `epoch.catalog.recipeBook`. Signed data must match the recipe's template exactly (`matchesDataTemplate`; LITERAL, HEX, DECIMAL and INTEGER segments, greedy, no trailing bytes) and is at most 128 bytes: preserve it byte for byte. A signature establishes wrapper provenance, not unbiased upstream data. With more than one source, a committed source other than the selected slot is fallback attempt (source − selected) mod count, with count = `sourceCountAt(epoch)`, and is valid only if its commit block is at least start + attempt × 20; replayEpochCommitment checks this.
4. A beacon epoch commits one drand round: its number in decimal as the data (1 to 19 digits, no leading zero), its scheduled time `genesis + (round − 1) × period` as the timestamp and the beacon's 64-byte BLS signature. For a beacon recipe `readEpochRecipes` adds the registration (`beacon`: verifier, chain hash, public key, genesis, period); with `{ blockTag }` it reads as of a block, for a registry whose implementation no longer has `beaconOf`, and needs an RPC that serves past state. `replayEpochCommitment` checks the round against the template, the timestamp against the schedule, the signature with `verifyBeaconRound` and the catalog's signer against `beaconSlotSigner(beacon)`; `replayCoordinator` does the same inside a full request replay. Replay does not call the registered verifier, so check the verifier's address and runtime code hash against the deployment manifest. The registry trusts that verifier's answer, and the owner vouches for a registration (`BeaconRegistered`). A drand signature shows what the beacon's key signed for the round, not that the beacon is unbiased or independent of its operators. Any round scheduled within 240 seconds before the publication block is valid, so the committer chooses which; one round can serve several consecutive epochs, so key an epoch on its epoch ID or epoch hash, never on its round.
5. Decode FulfillmentEvidence with decodeEvidencePacket and call replayCoordinator using trusted RequestContext. Bind BOTH requestBlock and targetBlock; derive the epoch from requestBlock and require targetBlock=max(requestBlock,committedBlock+1). Use its actual canonical hash and timely inclusion block/time. Never trust an expected key/seed supplied by the proof.
6. configuration.feeRecipient and configuration.initialMinFee must come from initialFeeRecipient and initialMinFee, the initialize arguments bound into protocolConfigurationHash, not the mutable feeRecipient or live pricing(); configuration.catalogHash stays the initial catalog even when the request's epoch used a scheduled one. Publication is open to `committer()` and to any wallet the owner allowed with `setBackupCommitter` (`isBackupCommitter`), and proof submission is open to anyone. `KeeperFeePaid` names the submitting wallet when `isAuthorizedCommitter` accepts it and `committer()` otherwise, so the payee is evidence of authorization, not of a different trust level, and neither changes the proof's validity. Compare transcript and commitments with both event and storage. Replayed computations do not authenticate RPC or prove receipt inclusion; apply finality/reorg policy.

## Robinhood Chain

A request binds a future drand evmnet round when it is made; the coordinator verifies the round's BLS signature and the VRF proof before accepting a result. Replay one fulfilled request with `@d20dao/vrf-sdk/round`:

```ts
import { JsonRpcProvider } from 'ethers';
import { D20_NETWORKS } from '@d20dao/vrf-sdk';
import { readRoundRequestEvidence, readRoundBeaconLogs, roundScheduleFromEvents, replayRoundRequest } from '@d20dao/vrf-sdk/round';

const network = D20_NETWORKS['robinhood-mainnet'];
const provider = new JsonRpcProvider(network.rpcUrl, 4663, { staticNetwork: true, batchMaxCount: 1 });
const evidence = await readRoundRequestEvidence(provider, network.coordinator, requestId);
const logs = await readRoundBeaconLogs(provider, network.coordinator, { fromBlock: network.deploymentBlock });
const verdict = replayRoundRequest(evidence, { schedule: roundScheduleFromEvents(network.coordinator, logs) });
```

`replayRoundRequest` never throws; `verdict.failed` names the failed checks among keyHash, configuration, beaconIdentity, beaconInForce, assignment (the round is the first one scheduled at least `ROUND_LEAD` = 3 seconds after the request block's timestamp), roundSignature, roundRandomness (sha256 of the signature), seed, proof, randomness, proofHash, evidencePacket, transcript, mappingHash, mappedResult, deadline and acceptance. `verdict.roundLeadSeconds` shows how long after the request the round was scheduled. The configuration binds the VRF key, the initial fee recipient and minimum fee, and beacon 0's identity (drand evmnet, `DRAND_EVMNET`). As on Arc, replay is mathematical: pin the coordinator implementation from the manifest and its `Upgraded` history, and take blocks, logs and timestamps from an RPC you trust. Public Robinhood RPCs serve no historical state, so read the implementation history from `Upgraded` logs rather than the ERC-1967 slot at past blocks.

Proof evidence is abi(Proof), 416 bytes, taken from the FulfillmentEvidence log. Single fulfillRandomness calldata is 452 bytes; fulfillRandomnessBatch carries up to 16 proofs, emits the same per-request events and FulfillmentSkipped(requestId, reason) for untouched members, so index and verify from events, never from calldata shape. Epoch evidence is abi(string canonicalRequest,Attestation), whose signature is 65 bytes for a signed record and 64 bytes for a beacon round. Neither has a version prefix; trusted emitter/event determines the decoder. Wrapper submissions remain verifiable through logs.

D20Proxy is atomically initialized; implementations are locked. Owner-authorized UUPS upgrades are a trust assumption and require storage/behavior review; renounceOwnership is disabled, so upgrade authority moves only through an accepted two-step transfer. Compatible upgrades must retain old accepted replay and pending requests. Reuse original initialized configuration and evidence, not current payout settings, live pricing or today's epoch packet.

Test fixture signatures and real captures (signed records or drand rounds) must be labeled honestly. Mapping alone does not verify origin, and callback failure does not invalidate accepted proof. Source admission, external review, upgrades and operational readiness remain separate from successful computation.

Block-end proxy storage alone cannot identify the code that executed a transaction. The public checker leaves implementation trust unknown if either boundary changes or any upgrade event occurs in the relevant block, including an A-to-B-to-A rollback. Exact attribution then requires transaction-ordered execution evidence. Match canonical finalized receipts as well as mathematical proof results.
